Die Plattform-Strategie (F1) beendet die Doppelpflege von `extends`, `package.json` und Migrations-Reihenfolge: **Manifeste sind die Single Source of Truth**, ein CI-Check erzwingt Konsistenz.

## Feature-Manifest (pro Layer)

Jeder Layer unter `packages/` hat ein `product.manifest.ts`:

```ts [packages/comments/product.manifest.ts]
import type { ProductManifest } from '../core/shared/types/manifest'

export default {
  key: 'comments',                 // === Ordnername
  tier: 'optional',                // abschaltbar? (foundation = nie)
  kind: 'product',                 // wen darf der Layer kennen? (s. u.)
  requires: ['moderation', 'admin'], // Layer, die dieser Layer voraussetzt
  hasMigrations: true,             // ⇔ scripts/migrations/ existiert
  userData: true,
  // + Katalog-Texte für die Produkt-Auswahl im Admin
} satisfies ProductManifest
```

`kind` ist die EINE Quelle für die Layer-Grenzen: `base` (nur `core` und `system`,
kennen nur einander), `foundation` (kennt nur `base`, nie ein Produkt oder eine Naht),
`seam` (verdrahtet mehrere andere) und `product` (kennt kein anderes Produkt).
`eslint.config.mjs` liest das Feld als Text — es steht deshalb immer allein in einer
Zeile: `  kind: '<wert>',`.

::warning
Manifeste dürfen **nur `import type`** verwenden — sie werden mit `--experimental-strip-types` geladen, Wert-Importe brechen das.
::

## Site-Manifest (pro App)

Jede App unter `apps/` hat ein `site.manifest.ts` — die Single Source der Feature-Wahl:

```ts [apps/comments/site.manifest.ts]
export default {
  siteId: 'comments',   // === App-Ordnername
  features: ['themes', 'admin', 'comments', 'posts' /* … */],
  // core + system sind implizit immer dabei — NICHT listen
}
```

## Der Check: `pnpm check:manifests`

`scripts/check-manifests.mjs` läuft als Teil von `pnpm check` (lokal und im CI-Job `lint`). Er prüft:

1. Jeder Layer hat ein Zod-valides Feature-Manifest, `key` = Ordnername, nur `import type`.
2. `hasMigrations` ⇔ `scripts/migrations/` existiert; jeder Layer mit Migrationen steht in der `LAYER_ORDER` von `scripts/migrate.mjs` (Drift-Erkennung in beide Richtungen).
3. Jede App hat ein Zod-valides Site-Manifest; Features existieren; `requires` ist **transitiv** erfüllt.
4. `extends` in der `nuxt.config.ts` = Features in kanonischer Reihenfolge (`EXTENDS_ORDER`) + `core` + `system` am Ende.
5. `@pukalani/*`-Dependencies in der `package.json` = exakt Features + `core` + `system`.
6. `apiPrefixes` im Manifest ⇒ das Plugin `server/plugins/product-manifest.ts` registriert es zur Laufzeit.
7. Jede Routen-Datei unter `server/api/` eines abschaltbaren Layers (`tier: 'optional'`) liegt unter einem seiner `apiPrefixes` — sonst erreicht die Notabschaltung des Produkts sie nicht. Die Routen liest der Check aus dem Dateibaum; Ausnahmen stehen mit Grund in `scripts/lib/manifest-routes.mjs`.
8. Keine globale `pageTransition` in einer App mit Dashboard.
9. **Lösch-Pflicht:** `userData` im Manifest (Pflichtfeld) passt zum Code — `true` verlangt den Beitrag für Auskunft und Löschung, `false` verträgt keine Migration mit einer Personen-Spalte. Tabellen und Spalten liest der Check aus den Migrationen.
10. **Datentür:** legt ein Layer `communityId` an, steht er in `scripts/lib/data-door-layers.mjs` (dort verbietet ESLint rohes `tablesDB`) oder mit Grund in der Ausnahmeliste.
11. **Einordnung:** `kind` aus dem geladenen Manifest = was der Text-Leser für ESLint sieht; `base` haben genau `core` und `system`; die Tabelle in `docs/CONCEPT.md` A14 führt jeden Layer unter der Überschrift seines `kind`.
12. **Abhängigkeiten über Auto-Import:** nutzt ein Layer einen Namen eines anderen Layers ohne Import-Zeile, steht dieser in `requires` (auch transitiv) oder ist `base`; ein Fundament-Layer braucht nie ein Produkt oder eine Naht (`scripts/lib/autoimport-coupling.mjs`).

## Zwei Felder, die Skripte und `/api/health` lesen

- **`appwriteProjects`** im Site-Manifest: die Appwrite-Projekte, gegen die Skripte im Namen der App schreiben dürfen. Der Migrations-Runner vergleicht sie mit der Projekt-Id der Env-Datei und bricht bei Abweichung ab (siehe [Migrationen](/architektur/migrationen)). Eine leere Liste heißt: Die App hat keine eigene Appwrite-Instanz.
- **`schema`** im Produkt-Manifest, Pflicht bei `hasMigrations: true`: `latest` ist die Nummer der höchsten Migration, `probe` nennt eine Tabelle oder Spalte, die es nach der jüngsten ablesbaren Migration geben muss. Daraus prüft `/api/health`, ob die Datenbank zum ausgerollten Programm passt. Der Test `packages/core/tests/schemaProbeManifests.test.ts` hält beides gegen die Dateien unter `scripts/migrations/`.

Zusätzlich enthält der Check den **Destruktiv-Guard** für Migrationen (siehe [Migrationen](/architektur/migrationen)).

::tip
Neue Layer und Apps **immer mit Manifest** anlegen — sonst schlägt die CI fehl. Der bequemste Weg für Apps ist [`pnpm create-site`](/guides/neue-app).
::

## Laufzeit-Gates

Die Feature-Wahl aus dem Manifest bestimmt, was gebaut wird. Zur **Laufzeit** kommen Config-Gates dazu (`app.config.ts`, Namespace `pukalani.*`, tief gemergt) plus Admin-Laufzeit-Toggles über `app_config` — Details unter [Core-Bausteine](/features/core-bausteine).
