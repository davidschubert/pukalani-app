## Der zentrale Runner

Schema-Änderungen laufen **immer** über den zentralen Runner — nie Layer-Scripts direkt mit hartem env-file aufrufen:

```bash
pnpm migrate --app <app>
```

Bei mehreren Apps ist `--app` **Pflicht** — sonst landet die Migration auf der falschen Appwrite-Instanz.

### Der Runner prüft sein Ziel

Seit 2026-11-16 glaubt der Runner keiner Env-Datei mehr ungeprüft (Vorfall 2026-08-31: 18 fremde Tabellen im Projekt `branding`, weil App und Datei nicht zusammenpassten):

- Jede App nennt in `site.manifest.ts` unter `appwriteProjects` die Projekte, gegen die sie migriert werden darf. Zeigt die Env-Datei auf ein anderes Projekt, bricht der Runner ab und nennt beide.
- Lässt sich das Manifest nicht laden, bricht er ab. Früher migrierte er dann alle Layer.
- Gegen einen Endpunkt, der nicht lokal ist, verlangt er `--prod`.
- `--dry-run` zeigt App, Projekt, Endpunkt und jede Datei in der Reihenfolge des Laufs und schreibt nichts.
- `--only <layer>-<NNN>` fährt genau eine Migration.

```bash
# lokal (apps/<app>/.env)
pnpm migrate --app branding

# Production: erst ansehen, dann fahren
pnpm migrate --app branding --env ~/.appwrite-secrets/migrations/branding.env --only brand-026 --dry-run
pnpm migrate --app branding --env ~/.appwrite-secrets/migrations/branding.env --only brand-026 --prod
```

`--env` ist dieselbe Angabe wie `--env-file`; über `pnpm` geht nur `--env` (die andere Schreibweise fängt Node ab, bevor der Runner sie sieht).

Jede Migrations-Datei beginnt mit `import '../../../../scripts/lib/assert-target.mjs'`. Direkt gestartet läuft sie lokal weiter; gegen einen anderen Endpunkt scheitert sie ohne Bestätigung. Der Test `packages/core/tests/scriptTargetGuard.test.ts` hält die Zeile fest — auch für jedes andere Skript, das einen Schlüssel in die Hand nimmt.

Der Runner führt die Migrationen aller Layer in der `LAYER_ORDER` (in `scripts/migrate.mjs`) aus; `check:manifests` hält diese Liste synchron mit den `hasMigrations`-Flags der Manifeste.

## Passt die Datenbank zum Programm?

Das Ausliefern läuft von selbst, Migrationen laufen von Hand und mit Freigabe. Damit es auffällt, wenn neues Programm vor seiner Migration live geht, nennt jeder Layer in seinem Manifest eine Probe:

```ts
// packages/brand/product.manifest.ts
schema: { latest: '026', probe: { migration: '026', table: 'brand_checks', column: 'erasedAt' } },
```

- `latest` ist die Nummer der höchsten Migrations-Datei.
- `probe` zeigt auf die jüngste Migration, deren Ergebnis sich am Schema ablesen lässt: eine Tabelle oder Spalte, die danach existiert und bleibt. Migrationen, die nur Indizes, Rechte, Ablagen oder Daten ändern, sind nicht ablesbar; die Probe bleibt dann auf der letzten ablesbaren stehen.

Die App fragt die Proben aller einkompilierten Layer mit ihrem eigenen Zugang ab (eine Zeile lesen, nur diese Spalte). `/api/health` meldet daneben `schema: { state, expected, found }` mit `state` = `ok`, `behind` oder `unknown`. Öffentlich sind nur dieses Wort und zwei Zahlen; welche Migration fehlt, steht im Server-Log (`schema.behind`). Das Feld `ok` der Seite bleibt davon unberührt.

Es gibt bewusst kein Register und keinen Zeiger: Eine einzeln von Hand gefahrene Migration würde einen Zeiger nicht bewegen, die Probe liest dagegen, was wirklich da ist.

**Neue Migration:** `latest` nachziehen. Legt sie eine Tabelle oder Spalte an, wandert auch `probe` dorthin. Der Test `packages/core/tests/schemaProbeManifests.test.ts` wird sonst rot.

## Regeln für Migrations-Scripts

Migrationen liegen pro Layer unter `packages/<layer>/scripts/migrations/` und sind:

1. **Idempotent** — HTTP 409 („existiert schon") wird übersprungen; jede Migration kann beliebig oft laufen.
2. **Additiv-sicher per Default** — zerstörerische Aufrufe (`deleteTable`, `deleteColumn`, `deleteIndex`, `deleteRow(s)`, `update*Column`) sind nur mit begründetem Marker erlaubt:

```ts
// destruktiv-ok: Spalte war nie produktiv befüllt, Guard prüft rowCount === 0
await tablesDB.deleteColumn(/* … */)
```

Ohne Marker schlägt `pnpm check:manifests` fehl (M3-Migrations-Audit).

3. **Column-Polling** — nach dem Anlegen von Columns auf Status `available` pollen, **bevor** Indizes darauf erstellt werden (Appwrite legt Columns asynchron an).

## MariaDB-Grenzen im Blick

Appwrite läuft auf MariaDB mit utf8mb4 (4 Bytes/Zeichen):

- Varchar-Spalten max. **16.381** Zeichen, Zeilenbudget insgesamt ~65 KB.
- Große Textspalten deshalb ≤ ~15k Zeichen planen.

## Neuer Layer mit Tables — Checkliste

1. `scripts/migrations/NNN-*.ts` im Layer anlegen (idempotent, additiv); erste Import-Zeile ist `import '../../../../scripts/lib/assert-target.mjs'`.
2. `hasMigrations: true` im Feature-Manifest setzen.
3. Layer in die `LAYER_ORDER` von `scripts/migrate.mjs` eintragen.
4. `pnpm check:manifests` → grün.
5. `pnpm migrate --app <app>` gegen die Ziel-Instanz.
